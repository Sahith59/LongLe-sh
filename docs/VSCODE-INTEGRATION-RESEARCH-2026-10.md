# VS Code integration contract research — 2026-10-05

**Scope:** Publicly installable LongLeash extension for phone ↔ IDE session control across repositories. This is a contract and design review, not a live provider acceptance test. Official pages were checked on 2026-10-05; installed extension **manifests only** were inspected read-only. No vendor bundle, webview state, personal transcript, or Marketplace credential was inspected.

## Decision

Build a LongLeash-owned VS Code conversation editor that is a client of the laptop daemon. The daemon remains the sole owner of provider sessions, write leases, approvals, and transcript ordering. Offer a separate, explicitly qualified Claude native-panel route through Anthropic's documented URI only after the exact installed build passes a disposable exact-history test. There is no documented Codex extension deep link or exported API to open a given thread in OpenAI's panel. VS Code's extension APIs permit LongLeash to create its *own* tree, webview editor, URI handler, commands, file links, and diffs; they do not grant access to another extension's private panel. [VS Code API](https://code.visualstudio.com/api/references/vscode-api), [Webview API](https://code.visualstudio.com/api/extension-guides/webview), [Claude VS Code](https://code.claude.com/docs/en/vs-code), [Codex app-server](https://learn.chatgpt.com/docs/app-server).

The `0.0.2` read-only companion is a useful connection and inventory slice, but it does **not** satisfy phone ↔ IDE control. It polls only the trusted local workspace's sessions, has one shared read credential, and implements no send, approval, Stop, ownership transfer, transcript editor, window registration, or phone-triggered open. The product's cross-repository request therefore needs a global daemon inventory plus per-window relevance, rather than treating the currently open workspace as the entire session universe. [Local field record](VSCODE-LIVE-INVENTORY-2026-10.md), [current server](../packages/daemon/src/ide-companion.ts), [current extension](../packages/vscode/src/extension.ts).

## Installed and repository evidence

- Local manifest versions at inspection: `Anthropic.claude-code` 2.1.289 and 2.1.283; `openai.chatgpt` 26.930.51102 and 26.917.62051. The manifests contribute UI commands and webview views, but show no declared cross-extension session API. This is **not** proof that activation exports nothing; only a documented public vendor export would be a release dependency. These versions differ from V0's tested Claude 2.1.229 and Codex 26.803.61601.
- `packages/protocol/src/ide.ts` already models per-window hello, capability negotiation, open instruction TTL, native record and asymmetric results. It correctly forbids reporting Claude `opened` from URI dispatch. `packages/vscode/src/contracts.ts` has preflight logic, but the installed `0.0.2` path does not expose control endpoints.
- `packages/daemon/src/codex-session-watch.ts` reads bounded Codex JSONL for passive native-panel discovery. That is a local observation fallback, not an app-server control channel. `packages/daemon/src/server.ts` receives Claude hooks. The field correction now waits for a matching nonempty transcript before passive Claude cards, avoiding the 36 lifecycle-only Orbit cards seen on the owner's phone. The real repeated-turn physical matrix remains open. [Field record](VSCODE-LIVE-INVENTORY-2026-10.md).
- The current companion endpoint shares a single token across windows and accepts a client-provided `clientInstanceId` and workspace hello. This is sufficient for its read-only preview under the local-user trust model. Mutations require daemon-issued per-window principals, short-lived operation IDs, capability grants, idempotency, revocation, and server-side canonical workspace validation. The `SecretStorage` copy is machine-local, but storing the same global token there does not make each window a separate principal. [SecretStorage](https://code.visualstudio.com/api/references/vscode-api#SecretStorage).
- `package.json` has `publisher: "longleash"`, `private: true`, `engines.vscode: ^1.94.0`, `extensionKind: ["ui"]`, and local VSIX packaging. These are build metadata, not evidence that the `longleash` Marketplace publisher is registered or controlled by the owner.

## Exact handoff design

1. **Discover:** The daemon stores a provider native ID and canonical cwd/worktree for each real conversation. Claude hooks supply session ID/cwd, with transcript proof before passive registration. Codex app-server's documented `thread/list`/`thread/read` supplies durable IDs and history; include `appServer` in `sourceKinds` and page through results. Passive file watch may repair missed native-panel activity, but must not assert control or liveness from mtime alone. Reconcile across all user-authorized repository roots; the VS Code tree defaults to **All sessions** with workspace grouping and a filter for **This window**.
2. **Register windows:** Each local trusted extension host registers a unique, revocable principal and exact canonical folder/worktree set. Track heartbeat, focus and build. Phone requests specify LongLeash session ID and desired destination; daemon resolves native ID and workspace, then selects an exact matching window or opens the folder and waits for its new registration. Multi-root membership must still identify the session's exact root. Do not send cross-repository content to a window merely because its label matches.
3. **Transfer ownership:** A read view can open while phone owns the provider, but send/approve/Stop require a daemon-issued lease. For takeover, interrupt or finish current turn, resolve pending approvals, close the old provider writer, verify exit, then reserve the new owner with a generation/fencing token. Reject stale operations after reconnect. The extension never directly starts a second Claude/Codex writer for a daemon-owned conversation.
4. **Open exact editor:** For Codex, daemon `thread/read` validates the requested ID and then supplies a bounded, paged transcript snapshot; live events come from its existing app-server connection. LongLeash's webview acknowledges only after rendering the same ID, workspace and lease generation. For Claude, the reliable in-IDE route is the LongLeash editor backed by the daemon's Claude SDK/session after a verified transfer; native-panel dispatch is an optional provider route with its weaker acknowledgement. The editor bridges typed send, approval, question, Stop, and review commands through the extension host, never from webview JavaScript directly to the daemon.
5. **Return:** “Continue on phone” releases IDE mutation ownership and gives the phone current event cursor, pending decision state and a verified native ID. It must not resume a second provider process while an IDE writer still exists. Reopen after reload/restart by re-reading daemon state; the webview's serialized state is only UI position, not transcript or lease authority. [Webview persistence](https://code.visualstudio.com/api/extension-guides/webview#persistence).

The older plan's “Claude native panel only” constraint should be revised if exact phone ↔ IDE control is the priority: the public URI is useful but cannot prove opening the exact session, and V0 already found a failing build. A LongLeash-owned Claude editor can give a verifiable path with the daemon as writer; it will be labeled **LongLeash conversation in VS Code**, not “Claude Code panel.” This design needs a real Claude SDK session-resume integration test, not an inference from the CLI flag alone.

## Explicit unsupported cases and release gates

- **Unsupported:** Programmatically opening a specified Codex thread in OpenAI's webview; reading or driving either vendor's private webview; treating manifest command IDs as session APIs; claiming exact Claude native open from OS URI success; using proposed VS Code APIs in a published build. [VS Code proposed API policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api).
- **Current fallback:** Exact copyable `claude --resume <id>` from the correct checkout, or Codex CLI thread resume where supported, with a warning to close an existing writer first. A fallback must preserve the native ID and workspace, not silently create a fresh conversation.
- **Contract tests:** VS Code extension host for URL handling, per-window registration, SecretStorage revocation, restricted mode, long/Unicode paths, multi-root and worktrees; protocol tests for lease generations, replay and mismatched ID rejection; app-server schema probes for `sourceKinds`, `thread/read`, resume, status, approvals and interrupt. Use stable fields for release; gate experimental methods separately.
- **Physical matrix:** Fresh Claude/Codex sessions from ordinary Terminal, integrated Terminal, vendor panel, phone and LongLeash editor. Verify one durable card per native conversation; phone → IDE → phone preserves full history and exact ID; approval/Stop/stream after sleep, reload, daemon crash, provider exit, multiple windows and concurrent pending handoffs. Retest Claude 2.1.289 (and any target release build) in a disposable workspace with exact history before enabling native URI dispatch. No testing of a private production conversation is required.
- **Release policy:** UI copy must distinguish **viewing**, **reserved to control**, **native URI dispatched**, and **exact conversation rendered**. If the session's workspace or writer cannot be verified, show an actionable blocked state and exact fallback.

## Marketplace status and prerequisites

The current release is a GitHub prerelease VSIX and local install path, not Marketplace publishing. Public search did not establish whether the `longleash` Marketplace publisher exists or is owner-controlled; that must be checked through the owner's publisher management account before a release. Microsoft requires a registered immutable publisher ID, matching manifest `publisher`, Azure DevOps/Marketplace publishing credentials, a production extension manifest, compliant README/assets, and a packaged extension; `@vscode/vsce` packages and publishes it. Microsoft currently documents global Azure DevOps PAT retirement on **2026-12-01** and recommends Entra ID based automated publishing, so the release pipeline should avoid baking in a global PAT. A Marketplace launch also needs removal of `private: true`, verified extension identity, explicit platform support (this build uses a Node UI host and local loopback), clean-install/upgrade tests, signed or verified artifact provenance, staged update and rollback. The existing package verifier and CI VSIX artifact are a useful start, but are not a publication gate. [Publishing extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension), [Extension manifest](https://code.visualstudio.com/api/references/extension-manifest), [Existing plan](VSCODE-EXTENSION.md).
