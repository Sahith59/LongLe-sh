# Audit of slices A1–A6 (2026-08-01)

A deliberate hunt for flaws, loopholes and overclaims before Phase A continues. Findings are
ordered by severity. Everything marked FIXED was addressed in the hardening pass that follows
this document; everything marked DEFERRED has a named phase and a reason.

## Critical — fixed in this pass

1. **No way to stop a running agent from the phone.** The adapter exposed `interrupt()` but
   nothing reached it. If an agent started doing something unwanted, the only remedy was
   denying its next approval — and an agent in a read-only loop never asks. A remote control
   with no stop button is a genuine safety hole. **FIXED:** `stopSession` typed operation,
   wired through the socket, with the session marked ended and its pending approvals closed.

2. **Orphan cleanup existed but was never called.** `ApprovalStore.closeOrphans()` was written
   and tested, yet no code path invoked it at startup. After a daemon crash, approvals stayed
   `pending` forever — a phantom inbox for prompts whose agent processes were long dead.
   **FIXED:** the daemon reconciles orphans on construction and reports how many it closed.

3. **Approvals never actually expired.** `sweepExpiredApprovals()` existed and was tested, but
   nothing ever ran it, so the 24-hour expiry was decorative and an unanswered approval could
   pin an agent indefinitely. **FIXED:** a sweep timer runs on an interval and is cleared on
   shutdown.

4. **The architecture doc claimed an audit log that did not exist.** Approval decisions carried
   `decidedBy`, but there was no record of who started or stopped what. Documenting a security
   feature that isn't implemented is worse than not having it. **FIXED:** an `AuditLog` records
   every mutating operation with the acting device, and the claim is now true.

## High — fixed in this pass

5. **Unbounded resource consumption from a paired device.** Nothing limited concurrent
   sessions, so a buggy client (or a stolen phone) could spawn agents until the laptop died.
   **FIXED:** a configurable concurrent-session cap, refused with a clear error.

6. **No WebSocket message size limit.** A single huge frame could exhaust memory before any
   validation ran. **FIXED:** a 1 MB cap at the socket layer.

7. **Sessions had no origin.** Everything looked identical in the list whether it was started
   from the phone, by the daemon, or (in future) attached from a terminal. A user cannot reason
   about an agent without knowing where it came from. **FIXED:** sessions carry an `origin` and
   the phone displays it.

## Medium — deferred, with reasons

8. **Agents started outside LongLeash are invisible.** A `claude` you launched yourself in a
   terminal or in the VS Code extension is a separate process; there is no supported way to
   inject an approval callback into it after the fact. This is a platform limit, not an
   oversight. Phase D mirrors such sessions through tmux (screen-exact, no structured
   approvals) and labels them honestly as mirror-only; the VS Code chat panel stays
   unreachable by design (webview isolation). **The product must never imply it controls what
   it can only watch.**

9. **Sessions are not persisted across daemon restarts.** Events survive (they are in SQLite),
   but the session list is rebuilt only from live processes, so after a restart the history is
   invisible even though the transcript exists. Phase F: a sessions table, reconstructing the
   list from the event log.

10. **The token travels in the WebSocket URL query string.** Fine over loopback and LAN with a
    short-lived token, but query strings leak into logs and proxies. Phase B moves the channel
    under TLS and passes credentials in the subprotocol header instead.

11. **The event log grows without bound.** `pruneBefore()` exists and is tested but nothing
    schedules it. Not urgent at personal scale (thousands of events per session), but a
    retention policy belongs in Phase F.

12. **`sendMessage` (steering an in-flight session without denying a tool) is unimplemented.**
    The protocol defines it and the server answers `not-implemented` honestly rather than
    dropping it. Needs SDK streaming-input mode; Phase E.

13. **Activity dedup can suppress a genuine repeat.** Auto-approved tools are keyed by name plus
    serialized input, so the same tool run twice with identical input reports once. Harmless
    for the feed's purpose; noted so it is not mistaken for a bug later.

## Accepted limitations, stated honestly

- **Shell commands are not parsed for paths.** The path guard covers tools that declare a path.
  Trying to infer writes from shell syntax would be security theatre, so `Bash` always reaches a
  human, who sees the entire command.
- **Contract tests are inherently non-deterministic.** They drive a real model; assertions target
  the mechanism (the approved path, the reported cwd) rather than any particular thing the model
  chooses to do.
- **`allowedTools` is not perfectly honored by the SDK.** A `Bash` invocation was observed running
  without a permission callback despite not being in the allowlist. The activity feed exists
  precisely so nothing runs invisibly, and `denyOutsideRoot` is defence in depth on top.
